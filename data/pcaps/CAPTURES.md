# Lab captures: STARTTLS / plaintext-auth test cases

Not committed to git (`data/pcaps/*.pcap` is gitignored — these are
reproducible lab artifacts, not source). This file documents how to
regenerate them and what each one demonstrates. Lab server only,
`127.0.0.1`, dummy credentials (`labuser`/`labpass`) throughout — see
CLAUDE.md.

## S17 — `S17_smtp_587_plaintext_auth.pcap`

SMTP submission (port 587) where the client authenticates with `AUTH
LOGIN` **without** ever issuing STARTTLS, even though the server
advertises `STARTTLS` in its EHLO capability response.

Generated with the lab mail server running (`docker compose up -d` in
`lab/docker/`) via:

```
swaks --to labuser@lab.test --from labuser@lab.test \
      --server 127.0.0.1:2587 -au labuser -ap labpass
```

(no `--tls` flag) while `tcpdump -i lo0 -w ... 'tcp port 2587'` captured
in parallel.

**Verified with tshark:**
- `tls.handshake.type` never appears anywhere in the capture — no TLS
  handshake ever occurs.
- Frame 15 payload decodes (base64) to `labuser`, frame 19 to `labpass`
  — the dummy credentials appear in cleartext on the wire. This is the
  expected/intended demonstration of plaintext auth before TLS (rule
  T-01), using dummy credentials only, per CLAUDE.md.

## S01b — `S01b_smtp_587_starttls_auth.pcap`

Same SMTP submission port (587), but the client issues STARTTLS before
authenticating.

Generated identically but with `--tls` added:

```
swaks --to labuser@lab.test --from labuser@lab.test \
      --server 127.0.0.1:2587 --tls -au labuser -ap labpass
```

**Verified with tshark:**
- Plaintext phase: `EHLO` → `STARTTLS` command (frame 11) → `220`
  success (frame 13).
- TLS ClientHello/ServerHello immediately follow (frames 15/17).
- `strings` over the whole pcap finds no occurrence of `labuser`,
  `labpass`, or their base64 forms — AUTH happened entirely inside TLS,
  so the credentials never appear in the clear.

## S18 — `S18_smtp_587_starttls_expired_cert.pcap`

STARTTLS SMTP on port 587, but the server presents `lab/certs/expired.crt`
instead of the normal `valid.crt`, to produce a real (not synthetic)
`CERT_EXPIRED` finding.

Generated by temporarily overwriting `lab/certs/valid.crt`/`valid.key`
(both gitignored, bind-mounted into the container) with the contents of
`expired.crt`/`expired.key`, restarting the container so Postfix rereads
them, then:

```
openssl s_client -connect 127.0.0.1:2587 -starttls smtp -tls1_2 \
        -CAfile lab/certs/ca.crt -quiet
```

TLS was pinned to 1.2 deliberately — TLS 1.3 encrypts the Certificate
message, so the expired cert would not be observable on the wire at all
(see CLAUDE.md's TLS 1.3 rule). `valid.crt`/`valid.key` were restored to
their original contents immediately after the capture.

**Verified independently of the analyzer, before running it:**
- `openssl s_client ... | grep Verify` reported `Verify return code: 10
  (certificate has expired)` and `Protocol: TLSv1.2`.
- `tshark` shows the Certificate handshake message (frame 17) containing
  DER bytes whose ASN.1 `notAfter` field decodes to `250928141124Z`
  (2025-09-28), matching `expired.crt` exactly.

**Then ran the analyzer** (`python -m core.analyze
S18_smtp_587_starttls_expired_cert.pcap`): reported `expired=True` and
fired `[HIGH] CERT_EXPIRED`, dropping the session score from 100 to 65.

## S19 — `S19_smtp_587_starttls_selfsigned_cert.pcap`

Same procedure as S18, using `lab/certs/selfsigned.crt`/`selfsigned.key`
instead:

```
openssl s_client -connect 127.0.0.1:2587 -starttls smtp -tls1_2 \
        -CAfile lab/certs/ca.crt -quiet
```

**Verified independently of the analyzer, before running it:**
- `openssl s_client` reported `Verify return code: 18 (self-signed
  certificate)`, with `subject=CN = mail.lab.test` equal to
  `issuer=CN = mail.lab.test`, and `Protocol: TLSv1.2`.
- `tshark` shows the Certificate handshake message (frame 17) present.

**Then ran the analyzer**: reported `self_signed=True`, fired `[MEDIUM]
CERT_SELF_SIGNED`, session score 80/100.

## S20 — `S20_smtp_587_shortlived_cert.pcap`

Regression fixture for the cert-expiry-uses-capture-time fix. A cert
signed by the lab CA, valid only from T-30s to T+90s relative to
generation, was swapped in as `valid.crt`/`valid.key`, the lab was
restarted, and a STARTTLS session was captured with `openssl s_client
-tls1_2` while the cert was genuinely valid (`Verify return code: 0`).
The original cert was restored immediately after. See the commit adding
`core/cert_parser.py`'s `reference_time` parameter for the full
before/after comparison - wall-clock evaluation of this cert will
permanently disagree with capture-time evaluation from now on, which is
exactly what makes it a durable regression test.

## S21 — `S21_smtp_25_plaintext_auth_mx.pcap`

Same scenario as S17 (`swaks` AUTH LOGIN without `--tls`), but on port
25 (mx/server-to-server role) instead of 587 (submission), to verify
T-02's role-aware severity downgrade against real traffic:

```
swaks --to labuser@lab.test --from labuser@lab.test \
      --server 127.0.0.1:2525 -au labuser -ap labpass
```

**Verified**: `python -m core.analyze` reports `T-01` as CRITICAL (role-
agnostic, same as S17) but `T-02` as INFO (vs. HIGH on S17's submission
port), confirming the mx/submission role split works on real captures,
not just synthetic `Session` objects. Contains the same intentional
cleartext dummy AUTH LOGIN exchange as S17.

## S22 — `S22_smtp_587_sha1_signed_cert.pcap`

STARTTLS SMTP on port 587 where the server presents a certificate signed
with SHA-1 instead of SHA-256.

`lab/gen_certs.py`'s `cryptography`-based signer refuses SHA-1 at the API
level (`UnsupportedAlgorithm`), so this cert was built with the `openssl`
CLI directly instead, chained to the lab CA with the correct SAN:

```
openssl genrsa -out leaf.key 2048
openssl req -new -key leaf.key -out leaf.csr -subj "/CN=mail.lab.test" \
        -config san.cnf -extensions v3_req   # san.cnf: subjectAltName=DNS:mail.lab.test
openssl x509 -req -in leaf.csr -CA lab/certs/ca.crt -CAkey lab/certs/ca.key \
        -CAcreateserial -out leaf.crt -days 365 -sha1 \
        -extfile san.cnf -extensions v3_req
```

Swapped in as `valid.crt`/`valid.key`, captured with `openssl s_client
-tls1_2` (same as S18/S19), restored immediately after.

**Verified independently of the analyzer:** `openssl s_client` reported
`Verify return code: 68 (CA signature digest algorithm too weak)` and
`Signature Algorithm: sha1WithRSAEncryption` in the leaf cert text.

**Then ran the analyzer**: reported `sig=sha1`, fired `[HIGH]
CERT_WEAK_SIGNATURE_HASH (X-07)`, session score 70/100.

## S23 — `S23_smtp_587_rsa1024_cert.pcap`

Same procedure, using an RSA-1024 leaf cert generated via
`lab/gen_certs.py`'s `build_leaf(ca_key, ca_cert, key_size=1024)` (this
one `cryptography` allows - only the signature hash restriction blocks
SHA-1).

**Verified independently:** `openssl s_client` reported `Server public
key is 1024 bit` and completed the TLSv1.2 handshake.

**Then ran the analyzer**: reported `RSA-1024`, fired `[HIGH]
CERT_WEAK_KEY (X-06)`, session score 70/100.

## S24 — `S24_smtp_587_wrong_sni.pcap`

STARTTLS SMTP on port 587, unmodified lab cert (SAN=`mail.lab.test`), but
the client requests a *different* hostname via SNI:

```
openssl s_client -connect 127.0.0.1:2587 -starttls smtp -tls1_2 \
        -servername notmail.lab.test -CAfile lab/certs/ca.crt
```

**Verified independently of the analyzer:**
- `openssl s_client -verify_hostname notmail.lab.test` (forcing openssl
  itself to check the hostname, which it doesn't by default) reported
  `Verify return code: 62 (hostname mismatch)`; the same command with
  `-verify_hostname mail.lab.test` reported `Verify return code: 0 (ok)`.
- `tshark -e tls.handshake.extensions_server_name` on the capture shows
  `notmail.lab.test` in the ClientHello.

**Then ran the analyzer**: fired `[HIGH] CERT_HOSTNAME_MISMATCH (X-05)`,
session score 70/100.

## S25 — `S25_smtp_587_no_sni.pcap`

Same as S24 but with `-noservername` instead, to test the "SNI absent"
case:

```
openssl s_client -connect 127.0.0.1:2587 -starttls smtp -tls1_2 \
        -noservername -CAfile lab/certs/ca.crt
```

**Verified**: `tshark -e tls.handshake.extensions_server_name` returns
nothing for this capture - confirmed no SNI extension was sent at all.

**Then ran the analyzer**: fired `[INFO] CERT_HOSTNAME_NOT_EVALUABLE`
(not `CERT_HOSTNAME_MISMATCH` - hostname match is never guessed when
there's no SNI to check it against), session score 95/100.

## S26 — `S26_smtp_2588_starttls_disabled.pcap`

First real (non-synthetic) capture for T-03 ("STARTTLS not offered at
all"). Required a second lab Postfix service, not just a cert swap: added
a `2588` listener in `lab/docker/postfix/master.cf` with
`smtpd_tls_security_level=none`, published as `127.0.0.1:2588`.

```
swaks --to labuser@lab.test --from labuser@lab.test --server 127.0.0.1:2588
```

(no `-au`/`-ap` - this capture doesn't attempt AUTH, so there's nothing
credential-related to redact-check.)

**Verified independently of the analyzer, before running it:**
- A raw `EHLO`/`STARTTLS` probe via `nc` confirms the EHLO capability
  reply has no `STARTTLS` line, and issuing `STARTTLS` anyway gets `502
  5.5.1 Error: command not implemented`.
- `tshark` confirms `STARTTLS` never appears anywhere in the capture
  (`tcp.payload` grep) and no TLS handshake occurs at all
  (`tls.handshake.type` is empty for every frame).

**Then ran the analyzer**: reported `capability_advertised_starttls=
False` (confirmed absent from a fully-observed EHLO reply, not just
unobserved) and fired `[HIGH] T-03`, session score 5/100 (also hit by
the pre-existing `NO_TLS_OBSERVED` CRITICAL finding, since this session
never uses TLS at all).

## S27 — `S27_smtp_587_tls1_0.pcap`

STARTTLS SMTP on port 587, unmodified lab server, client forced to
TLS 1.0.

Plain `openssl s_client -tls1` fails on this machine's OpenSSL 3.0.18
with `legacy sigalg disallowed or unsupported` (the default security
level blocks TLS 1.0's older ServerKeyExchange signature scheme). Adding
`-cipher DEFAULT@SECLEVEL=0` unlocks a genuine handshake:

```
openssl s_client -connect 127.0.0.1:2587 -starttls smtp -tls1 \
        -cipher "DEFAULT@SECLEVEL=0" -CAfile lab/certs/ca.crt
```

**Verified independently of the analyzer:** `openssl s_client` reported
`Protocol: TLSv1`, `Cipher is ECDHE-RSA-AES256-SHA`, `Verify return code:
0 (ok)`, and real SMTP application data (`250 CHUNKING`, `221 2.0.0
Bye`) flowed afterward - not just a cosmetic protocol label. `tshark`
confirms `tls.handshake.version = 0x0301` (TLS 1.0) on both the
ClientHello and ServerHello.

**Then ran the analyzer**: fired `[HIGH] TLS_VERSION_1_0 (P-02)`,
session score 70/100.

## Weak cipher suites (RC4/3DES/NULL/anonymous-DH) - not captured

Genuinely attempted, not faked. Three approaches tried:

1. Local macOS OpenSSL 3.0.18: `openssl ciphers -v 'ALL@SECLEVEL=0'`
   lists no RC4/3DES suites at all - they are not compiled into this
   build, regardless of security level.
2. Python's `ssl` module (same underlying system OpenSSL): same result,
   `ctx.set_ciphers('RC4')` raises `No cipher can be selected`.
3. A Debian Jessie (2016, OpenSSL 1.0.1t) container, run on the lab's
   own `docker_lab-isolated` network as the TLS *client*, with real
   RC4/3DES cipher suites available
   (`openssl ciphers -v ALL | grep RC4` lists `RC4-SHA`,
   `DES-CBC3-SHA`, etc.). Connecting to `securemailscope-lab-mail:587`
   with `-cipher RC4-SHA` or `-cipher DES-CBC3-SHA` still fails with
   `sslv3 alert handshake failure` - the lab **server** (Debian
   bookworm, OpenSSL 3.0) doesn't support these ciphers either. Weak
   cipher negotiation needs both sides to agree; getting a real capture
   would require building an entirely separate legacy Postfix/Dovecot
   image on an old base (itself complicated by Debian Jessie's own EOL
   package repos requiring `archive.debian.org` and
   `--allow-unauthenticated` just to install `openssl`), which was
   judged out of scope for this "if time remains" item.
